Aibarangay System Audit

A React + Vite single-page app with three portals — a public website, a resident portal, and a barangay operations console. The routing, layouts, and component libraries are complete and coherent. What connects the three portals is nothing: every screen is fed by its own static mock file, and no data ever leaves the browser.

The app is a finished frontend prototype of a civic reporting system. The core product promise — a resident reports a problem, the barangay resolves it — does not function end-to-end, because there is no backend, no authentication, and no shared data.

What is missing

  1. No backend, no persistence — nothing leaves the browser

    A search of the whole src/ tree finds zero fetch/axios calls, no React Context, no store, and no localStorage for reports (the only localStorage use is remembering sidebar collapse in the two layouts). Every list on every page — reports, incidents, notifications, messages, analytics — is a hand-written array in src/data/*.js. Upvotes, status changes, and new reports vanish on refresh.

  2. Authentication is cosmetic

    LoginPage.jsx:25-39 accepts any syntactically valid email plus any password, shows a "Sign-in accepted (demo)" notice, and navigates by tab choice. There are no route guards: typing /admin/audit-logs or /resident/messages as an anonymous visitor works. The register page collects a full profile and discards it.

  3. The core loop — report → review → resolve → notify — is disconnected

    Submit in ResidentReportProblem.jsx only sets a "submitted" flag. residentData.js MY_REPORTS and adminData.js REPORTS are unrelated arrays that merely share demo content, and the public map reads a third (publicData.js MAP_MARKERS). The barangay never sees a new report; the admin review decision in BarangayReviewReport.jsx:19-22 also only sets local state before navigating away. Four places render "the same" incidents from four datasets.

  4. An entire first version of the app is dead code

    App.jsx never routes to pages/LandingPage.jsx, so it and the twelve root-level components it pulls in — Navbar, Hero, Footer, HowItWorks, CommunityProblems, CommunityMapPreview, AiGisSection, TransparencySection, CtaSection, TrustImpact, ReportModal, HelpModal, AuthModals — plus mockProblems.js are unreachable. portalData.js appears to have no importers either (verify before deleting). That is roughly a quarter of the component tree shipped in every build.

  5. Duplicated concepts instead of shared ones

    Two different CommunityMapPreview components exist (components/ and components/public/); CtaSection vs CTASection; three map components (MapMockup, ResMap, GisMap) each re-wrap the same Leaflet setup; CommunityMapPage and ResidentMap are near copies. Nothing is shared across portals because there is no shared layer to put it in.

  6. Smaller gaps

    No tests of any kind; no error boundary; resident messages and notifications are static with no send path; evidence "upload" only pushes a filename into local state (ResidentReportProblem.jsx:70-81) — no file is read or attached; demo images are hotlinked from Unsplash; the "AI" confidence/duplicate scores everywhere are hard-coded numbers, not a model.

What is genuinely built well

  • Routing is complete and tidy — all 33 routes across three layouts in App.jsx, with redirects and a detail route (/admin/reports/review/:id).
  • Three coherent design systems (public, resident teal, gov console) with per-portal CSS and barrel index.js exports.
  • Real Tagum City geography: Leaflet maps with actual coordinates and a tagumBarangays.js dataset.
  • Consistent accessibility attention — skip links, aria-labels, aria-current on wizard steps, focus states, reduced-motion in the scroll effects.
  • The 5-step report wizard has real client-side validation, geolocation pinning, and a guided UX that would survive being pointed at a real API.

Suggested build order

  • Stand up an API + database for reports (Supabase or Express + Postgres fits this stack), and replace the arrays in adminData.js/residentData.js with fetches — one source of truth makes stages 3–5 live immediately.
  • Add real auth with route guards in the resident and admin layouts (Supabase Auth or JWT; protect /admin/* by role).
  • Wire the wizard's submit to a POST and the reference number to the server response; show it in My Reports from the DB.
  • Make admin actions mutations — review decisions, assignments, and status changes write back and notify the resident.
  • Delete the dead column — LandingPage, the twelve root components, mockProblems.js, and (after checking) portalData.js — then deduplicate the map components.
